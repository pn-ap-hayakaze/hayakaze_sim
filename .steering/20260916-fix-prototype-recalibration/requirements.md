# 要求内容: プロトタイプを確定設計決定に合わせて再較正する

作成日: 2026-09-16
対象: `prototype/`（エンジン検証プロトタイプ）

## 背景

設計フェーズで約60の設計決定が確定した。そのうち2つ（**両リーグDH**と**クラッチの係数化**）が、
`prototype/` で較正済みだった打席エンジンの中核を無効化している。この状態で `docs/` に仕様を書くと、
誤った較正目標（「セはDHなし」前提の SLOPE と較正表、置換方式のクラッチ）が仕様に固定される。
したがって永続ドキュメントより先にプロトタイプを直す。

あわせて、設計レビューで確認された「較正の検証を成立させるための前提」3件（乱数の独立ストリーム、
較正アサートの自動化、疲労診断スクリプトの誤り）と、DH を型に入れる作業を同じ作業単位で扱う。

## 変更・追加する機能

順序に意味がある。1 を直さないと 5 の数字の変化がモデル由来か乱数整列由来か切り分けられず、
2 は 5 の完了判定そのもの、4 は 5 で全球団に DH が常設される前提になる。

### 1. 乱数を用途別・試合別の独立ストリームにする

- 現状: `season.ts` が単一の `season.rng` を全858試合に順番に渡している。10日目に `rng.next()` を1回余分に呼ぶだけで12球団すべての勝敗が変わり、優勝球団が入れ替わる（C03 91勝→78勝、C06 56勝→69勝）
- 現状: `Rng.state` が private でゲッターもセッターもなく、乱数状態をセーブデータに書き出せない
- 変更: 試合用の乱数を `hash(masterSeed, seasonYear, day, gameId)` から試合ごとに派生させる
- 変更: 故障・スカウト観測・成長・AI意思決定が将来それぞれ独立ストリームを持てる形（用途を識別子で分ける派生関数）にしておく。今回は試合用のみ実装し、他用途の派生口だけ用意する
- 変更: `Rng` に `serialize()` / `restore()` を足す

### 2. vitest と較正アサートを入れる

- 現状: `package.json` に test スクリプトがなく、vitest も jest もない。検証は `validate.ts` が数字を印字して人間が目で見る方式で、較正値を検証するアサートはゼロ
- 変更: vitest を devDependencies に入れ、`npm test` を追加する
- 変更: 5シード以上でリーグ水準が目標レンジに入ることを**許容幅つき**でアサートする回帰テストを書く
- 検証項目: 打率・出塁率・OPS・防御率・WHIP・1試合平均得点（README 較正表の項目）に加え、レビューで抜けが判明した **1チームあたりの盗塁企図数と盗塁成功率**
- 乱数独立性（タスク1）のテストもここに含める
- **このテストはタスク5を終えるまで落ちる。それが正しい挙動である**

### 3. `diag-fatigue.ts` の回復式を直す

- 現状: `diag-fatigue.ts:15` が `10 + stamina × 0.25`、実体の `season.ts:63` は `10 + recovery × 0.2`。diag 側のコメントは「season.ts の dailyRecovery と同じ式（診断用に写している）」と書いてある。疲労診断はこれまで誤った数字を出していた
- 変更: 式を写すのをやめ、`season.ts` の `dailyRecovery` を export して import する
- 変更: `scripts/` 全体で同じ「写している」パターンがないか確認する（grep 済み: 該当は `diag-fatigue.ts` の1箇所のみ。`_rev_*.ts` にも SLOPE の写しがあるが削除対象）
- 変更: 修正後に 3連投・4連投・5連投以上の年間発生回数、完投数、1試合最多球数、盗塁企図を測り直し、README の既知の問題に記録する。**疲労モデル自体の修正はしない**

### 4. DH を打順の枠として型に入れる

- 現状: `ratings.ts:8` の `POSITIONS` は守備位置9個で、コメントに「+ 指名打者」とあるのに配列にない
- 変更: `POSITIONS` は守備位置9個のまま維持し、打順の枠（守備位置9個 + DH）を表す別の型を立てる
- 制約: `FieldingByPosition = Record<Position, number>` に DH を足さない（全選手に無意味な「DHの守備力」が生まれる）
- 変更: `advanced.ts` の守備位置補正を最小限だけ直す
  - `POSITIONAL_ADJUSTMENT_PER_162` に DH の枠を足す（FanGraphs の MLB 値 −17.5）
  - `positionalRuns()` を `primaryPosition` 固定から「実際に出場したポジション別の出場内訳」で計算する形にする
  - そのために `BattingStats` にポジション別の出場内訳（試合数）を持たせ、`game.ts` で記録する
- スコープ外: 守備位置補正の NPB（DELTA）値への全面差し替え

### 5. 両リーグDHにして SLOPE を再較正する

- 現状: `teams.ts:148` の `usesDh()` が `league === 'PACIFIC'` を返し、`game.ts:100` がそれを使う。決定は両リーグDH
- 実測されている影響: セ球場開催で R/G 3.853→4.164（+8.1%）、OPS .692→.721。リーグ防御率が 3.43→3.62 のように上振れし、WHIP が5シード中4つで上限 1.35 を、出塁率が3つで上限 .325 を超える
- 変更: DH の有無を `LeagueId` から剥がし、**リーグ設定**（DH有無・同一リーグ内対戦数・交流戦対戦数・球団リスト）として外に出す。`game.ts` / `schedule.ts` / `generateLeague` が引数で受け取る。`usesDh` は廃止する
- 根拠: 決定「球団数・リーグ数・リーグごとの球団数をハードコードしない」
- 変更: `profile.ts` の SLOPE を再調律し、両リーグDHの状態でリーグ水準を目標レンジに戻す
- 制約: 打者側と投手側の SLOPE の非対称（batterHR 0.33 vs pitcherHR −0.16、batterK −0.23 vs pitcherK 0.12）を**さらに深めない**。この非対称は Odds Ratio 法の「打者と投手が打ち消し合う」安定性を弱め、多シーズンでの得点環境漂流の原因になっている
- 変更: README の較正結果表を新しい数字で書き直し、何をどう変えたか・なぜその値にしたかを記録する

### 6. クラッチを係数型にする

- 現状: `profile.ts:104` が `contact = risp ? b.clutch : b.contact`（置換、しかもコンタクトを置換）。`profile.ts:148` が `hits = (risp ? p.clutch : p.hits) − fatiguePenalty`（置換）
- 決定: 得点圏では**ミートに係数を掛ける**。`実効ミート = meetAgainst(b, throws) × f(clutch)`、`f(50) = 1.0`。投手側も `hits` に同型の係数を掛けて対称にする
- 決定: クラッチは「そうそう高くならない」。上側の裾が薄い分布（正規ではない）で生成する
- 未決定（design.md で提案し承認を得る）: 係数 f の傾き、クラッチの生成分布の形
- 較正の手がかり:
  - 置換方式の実測: クラッチと打者WARの相関 0.061、得点圏打率との相関 0.179
  - 置換方式では真の（得点圏打率 − 通常打率）の選手間 σ が約20ポイント。The Book のクラッチ才能 σ は約8 wOBA ポイント
  - **係数型にしたうえで、真のクラッチ才能の幅が 6〜8 wOBA ポイント程度**に収まるように傾きを決める
  - 得点圏の打席は全打席の 24.9%
  - 置換方式では階層（主砲とベンチ）とプラトーン差（左右別ミート）が得点圏で消えていた。係数型なら保たれるはずなので確認する
- 変更: `ratings.ts` のクラッチのコメント（「contact の代わりに使う」）を係数型の記述に直す
- 変更: `generate.ts` / `arsenal.ts` のクラッチ生成を新しい分布に差し替える

### 片付け

- `prototype/scripts/_rev_caps.ts` `_rev_clutch2.ts` `_rev_math.ts` `_rev_season.ts` を削除する（設計レビューの使い捨てスクリプト。`npm run typecheck` もこの2ファイルで失敗している）

## ユーザーストーリー

- 設計者として、両リーグDHとクラッチ係数型という確定決定のもとで較正されたリーグ水準を知りたい。そうすれば `docs/` に書く較正目標が正しい前提に立つ
- 設計者として、SLOPE やモデルを変えたとき「較正が崩れていないか」を `npm test` 一発で知りたい。目視で表を読む方式では回帰に気づけない
- 設計者として、ある試合の乱数消費が他の試合の結果に波及しないことを保証してほしい。そうでないと再較正の数字の変化を説明できず、将来セーブ&ロードで結果を引き直せてしまう
- 設計者として、診断スクリプトが実体と同じ式で動いていることを保証してほしい。診断が嘘をつくと較正目標そのものを誤って書く

## 受け入れ条件

1. 両リーグDHの状態で `npm run validate` が5シード以上で目標レンジに収まる
2. `npm test` が通る（較正アサート・乱数独立性・盗塁企図と成功率を含む）
3. `npm run typecheck` が通る
4. README の較正結果表が新しい数字で書き直され、既知の簡略化・既知の問題が更新されている
5. `npm run diag:fatigue` が実体と同じ式（`dailyRecovery` の import）で正しい数字を出す
6. 乱数ストリームが独立していて、ある試合の乱数消費回数を変えても他の試合の結果が変わらない（テストで自動検証）
7. `Rng` の状態を `serialize()` で書き出し `restore()` で復元すると、以後の乱数列が完全に一致する
8. `POSITIONS` は9個のまま、DH を含む打順枠の型が別に存在し、`FieldingByPosition` に DH がない
9. `usesDh` が存在せず、DH有無・試合数・対戦数・球団リストがリーグ設定として `game.ts` / `schedule.ts` / `generateLeague` に引数で渡っている
10. クラッチが係数型（`f(50)=1.0`、打者はミート、投手は hits に乗算）で、真のクラッチ才能に起因する（得点圏 wOBA − 通常 wOBA）の選手間 σ が 6〜8 wOBA ポイント程度に収まる。リーグ全体の得点は係数化の前後で変わらない
11. 得点圏で階層差（主砲 vs 控え）とプラトーン差（左右別ミート）が保たれている（数値で確認）
12. `_rev_*.ts` 4ファイルが消えている
13. 疲労・完投・盗塁企図の実測値（正しい診断で測り直した数字）が README の既知の問題に記録されている

## 較正目標（参照）

出典は `npb-calibration-targets` と README。

| 指標 | 目標レンジ |
|---|---|
| 打率 | .240〜.260 |
| 出塁率 | .305〜.325 |
| OPS | .660〜.715 |
| 1試合平均得点（1チーム） | 3.6〜4.3 |
| 防御率 | 3.00〜3.60 |
| WHIP | 1.24〜1.35 |
| 盗塁企図 1チーム | 105〜110（セ・パ合成。リーグ差は設けない決定） |
| 盗塁成功率 | .65〜.75 |
| 規定投球回の先発 防御率 σ | 約0.65 |

**注意（ベースライン実測）**: 現行コード（セDHなし）でも seed 1 は防御率 3.67・WHIP 1.386、seed 3 は防御率 3.76・WHIP 1.372 で、既に目標上限を超えている。
シード間の防御率の幅は約 0.4 あり、目標レンジの幅 0.6 と同程度。したがってテストの許容幅は
「全シードが目標レンジに厳密に入る」ではなく「複数シードの平均が目標レンジに入り、各シードは目標レンジを一定幅だけ広げた帯に入る」
という2段構えにする必要がある。具体的な幅は design.md で決める。

## 制約事項

- 変更は `prototype/` 配下に限る。`docs/` はまだ存在せず、本作業では作らない
- **やらないこと**（実装フェーズで別の `.steering/` を切る）:
  - 二軍、投げ抹消、65名ロスター、引退、自由契約、一軍登録と抹消
  - 球団名と球場名の差し替え
  - 守備位置補正の NPB（DELTA）値への全面差し替え
  - 疲労の soft gate、先発の球数分散、盗塁企図の修正（測って記録するだけ）
  - 打球の質の中間層、守備WAR、捕手フレーミング
  - 契約、FA、コーチ、ドラフト、スカウト推定の実装
  - リーグ平均アンカーの動的差し替え
- SLOPE の打者・投手非対称を深めない
- `POSITIONS` に DH を足さない。`FieldingByPosition` に DH を足さない
- エンジン内で `Math.random()` を使わない（既存方針）
- コミットは作業完了後に確認してから行う
